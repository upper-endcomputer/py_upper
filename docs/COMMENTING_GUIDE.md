# 中文代码注释规范

本规范适用于本仓库跟踪的 Python、C/C++、测试、构建脚本与配置。`.tmp/`、下载依赖、生成的 C、runtime 和 dist 是产物，不应逐个手改；修改生成器或原始源码。第三方源文件保留原版权及上游说明，项目补充说明明确标注归属。

## 文件与接口

- 每个代码文件用中文交代职责、调用边界或关键约束；包入口说明导出边界。禁止以“这里执行函数”等复述语法的句子凑覆盖率。
- Python 接口使用三引号 docstring，先写行为摘要，再按需要写 `Args`、`Returns`、`Raises`、副作用与并发约束。中文解释配合真实参数名，不重复已有类型标注。
- C/C++ 文件使用 Doxygen `@file`、`@brief`、`@note`；公开接口按需添加 `@param`、`@return`、`@pre`。指针所有权、长度单位、编码和配对释放必须明确。
- 局部注释说明为什么需要该分支、平台差异或算法不变量；不要逐行翻译赋值和循环。
- 测试说明被验证的契约、fixture 假设与不能证明的范围。mock、headless、真实桌面和正式签名必须区分。
- 不在字符串、生成代码模板或协议数据中机械替换英文；它们可能是运行输入。已有英文历史说明可保留，中文说明必须与实现一致。

## 非代码文件

支持注释的配置使用本格式的注释符。严格 JSON、类型标记与许可证通过 [逐文件索引](FILE_MAINTENANCE_INDEX.md) 说明，不能加入会破坏解析的字段或注释。Markdown 已是说明文档，维护其内容和入口，不额外堆积无效文件头。

## 审查与验证

1. 先读实现，再写职责、输入输出、失败和所有权；不得从名称自动推断并批量生成接口契约。
2. 注释变更优先比较 Python AST 和 C/C++ 非注释内容，确认没有改动运行字符串、宏或指令。
3. 发现行为缺陷时单独添加失败回归，验证修复；注释覆盖检查不能证明逻辑审计完成。
4. 执行 `python tools/check_comments.py` 检查跟踪文件覆盖，再串行执行 pytest，避免与真实构建争用工作区锁。
5. 全文件维护说明是第一层覆盖；它不等于所有函数、算法和第三方代码都经过逐行审计。深层接口说明必须根据实际阅读补充，不能把文件头覆盖冒充完成。
